## 🧟 Shadow API vs Zombie API

| 구분 | Shadow API | Zombie API |
|---|---|---|
| 정의 | 존재 자체를 조직이 **모르는** API | 죽었어야 하는데 **살아 있는** API |
| 명세상 상태 | 없음 | 있었거나 폐기 표시됨 |
| 조직의 인지 | 모름 | 알았지만 잊음 / 폐기했다고 믿음 |
| 발생 원인 | 승인 없는 배포, 테스트·디버그 엔드포인트, 문서화 누락 | v2 배포 후 v1 미삭제, 폐기 절차 부재 |
| 보안 수준 | 보안 검토를 받지 않은 경우 多 | 최신 보안 정책 미적용 |
| 탐지 기준 | 관측·자산 − 명세 | 명세상 deprecated ∩ 관측·자산 |
| 통관·물류 예시 | 포워더 테스트용 화물조회 API 운영 중 | EDI→REST 전환 후 구버전 신고 조회 API 응답 |

> 🔁 둘 다 **"인벤토리와 현실의 불일치"** 가 뿌리. Zombie는 담당자가 바뀌면 Shadow가 된다.

**파생 분류**
- **Orphan / Ghost** — 소유자 정보 없음, 자동화로 되살아나기도 함
- **Dormant 노출** — 트래픽 없지만 외부에 열림 (미러링만으론 안 보임)
- **Phantom 명세** — 명세에만 있고 실제론 없음 (문서 품질 문제)

## ☁️ 자동화 클라우드의 미정리 자원 위험

**왜 더 많이 남는가**
- 생성은 자동, 삭제는 수동
- GitOps·오토스케일링이 주인 없는 서비스를 계속 되살림
- 개발·플랫폼·클라우드·보안 팀의 책임 분산
- 퇴사·팀 개편 후 자원·자격증명 방치
- IaC 드리프트, 점검 주기(월·분기)와 노출 시간(분·시간)의 불일치

| 유형 | 위험 |
|---|---|
| 잊힌 API 엔드포인트 | 최신 인증·레이트리밋 미적용 상태로 노출 |
| 남은 자격증명 | 정상 사용자처럼 접근 → 탐지 어려움 |
| 과도한 권한의 역할 | 다른 취약점과 결합 시 피해 확대 |
| 댕글링 DNS | 서브도메인 탈취로 도메인 신뢰 악용 |
| 열린 네트워크 규칙 | 내부용 서비스 외부 노출 |
| 방치된 데이터 사본 | 개인정보·설정 유출 |
| 고스트 워크로드 | 패치 없이 장기 실행, 침해 시 은신처 |
| 방치된 파트너 연동 | 계약 종료 외부 주체가 계속 접근 |

> ⚠️ 핵심은 "취약하다"가 아니라 **"아무도 보지 않는다"**. AI 기반 정찰 자동화로 이런 자원이 발견되는 속도가 빨라지고 있다.

## 🚢 왜 통관·물류인가

| 업종 | 적합도 | 메모 |
|---|---|---|
| **통관·무역 물류** | ★★★★★ | 파트너 API 다수, 다국적 트래픽, EDI→API 전환기, 관세청·AEO 거버넌스 |
| 대학·공교육 | ★★★★☆ | 소규모 서비스 다수, 비K8s 레거시 위주 |
| 키오스크 | ★★☆☆☆ | 디바이스 보안 성격 |
| 스마트그리드 | ★☆☆☆☆ | OT 중심, 재현 불가 |

**모의 통관·물류 플랫폼 시나리오**

| 서비스 | 심어둘 시나리오 |
|---|---|
| 수출입신고 | 구버전 v1 조회 API 잔존 (Zombie) |
| 화물조회 | 포워더 테스트용 API 미등록 (Shadow) |
| 관세사·포워더 연동 게이트웨이 | 계약 종료 파트너 키·엔드포인트 (Orphan) |
| 해외 세관 연동 | 트래픽 없는 국가별 엔드포인트 노출 (Dormant) |
| 관세 계산 | 정상 서비스 (대조군) |
