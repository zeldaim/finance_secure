# 02. 자동화된 클라우드 환경에서 정리되지 않은 자원의 악용 가능성

> 목적: Shadow/Zombie API가 "API만의 문제"가 아니라, 자동화된 클라우드 운영에서 **정리되지 않은 자원 전반**의 문제임을 보여주는 원인 분석 파트.
> 범위: 방어 관점의 위험 분류. 실제 확인은 프로젝트가 통제하는 실습 계정에서만 수행한다.

---

## 1. 왜 자동화 환경에서 더 많이 남는가

| 요인 | 설명 |
|---|---|
| 생성은 자동, 삭제는 수동 | IaC·CI/CD로 자원은 몇 초 만에 생기지만, 삭제는 사람이 기억해야 함 |
| 자동 복구가 "고스트"를 유지 | GitOps·오토스케일링·자동 재시작이 주인 없는 서비스를 계속 되살림 |
| 책임 분산 | 개발(코드)·플랫폼(K8s)·클라우드(계정)·보안(점검)이 각자 일부만 봄 |
| 사람의 이동 | 퇴사·팀 개편 후 자원과 자격증명이 인수인계 없이 남음 |
| IaC 드리프트 | 콘솔에서 수동 변경 → 코드와 실제 상태가 달라져 코드 기준 점검에서 누락 |
| 점검 주기 불일치 | 월·분기 점검 vs 분·시간 단위로 생기고 사라지는 자원 |

## 2. 미정리 자원 유형별 위험

| 유형 | 예시 | 위험 | 관련 OWASP API |
|---|---|---|---|
| **잊힌 API 엔드포인트** | 개발·테스트 스테이지, 구버전 API, 직접 노출된 함수 URL | 최신 인증·레이트리밋 정책 미적용 상태로 외부 노출 | API9, API2, API4 |
| **남은 자격증명** | 퇴사자·종료된 프로젝트의 액세스 키, API 키, 서명 키 | 폐기되지 않은 키로 정상 사용자처럼 접근 → 탐지 어려움 | API2 |
| **과도한 권한의 역할** | 테스트 때 넓게 준 IAM 역할·서비스 계정 | 다른 취약점과 결합 시 피해 범위 확대 | API5 |
| **댕글링 DNS** | 삭제된 자원을 가리키는 DNS 레코드 | 서브도메인 탈취로 조직 도메인 신뢰를 악용한 피싱·세션 탈취 | — |
| **열린 네트워크 규칙** | 임시로 연 0.0.0.0/0 보안그룹, NodePort | 내부용 서비스의 외부 노출 | API8 |
| **방치된 데이터 사본** | 공개 설정 스냅샷, 백업 버킷, 로그 버킷 | 개인정보·설정 정보 유출 | API3 |
| **고스트 워크로드** | 주인 없는 Pod·데몬·배치 작업 | 패치되지 않은 채 장기 실행, 침해 시 은신처가 됨 | API9 |
| **방치된 파트너 연동** | 계약 종료된 파트너용 API·키 | 외부 주체가 여전히 접근 가능 | API10 |

## 3. 위험이 커지는 구조 — "조용한 노출"

```
 자동화로 생성 ──▶ 담당자 이동/잊힘 ──▶ 인벤토리·모니터링에서 빠짐 ──▶ 패치·정책 갱신 중단
                                                                    │
       피해 인지 지연 ◀── 비정상 접근도 "보는 사람 없음" ◀── 외부에서 발견 ◀┘
```

- 핵심은 **"취약하다"가 아니라 "아무도 보지 않는다"** 는 점이다.
- 최근 공격 자동화(AI 기반 정찰 도구 포함)로 외부 노출 자산을 찾는 비용이 크게 낮아져, 이런 자원이 발견되는 속도가 빨라지고 있다.

## 4. 참고 사건 (원문 확인 필요)

| 사건 | 연결 지점 |
|---|---|
| SK텔레콤 유심 정보 유출 (2025) | 서버에 장기간 숨어 있던 악성코드 → 고스트 워크로드·장기 미탐지 |
| 쿠팡 개인정보 유출 (2025) | 폐기되지 않은 인증 관련 키가 악용됐다는 정황 → 남은 자격증명 |
| Optus (2022) | 인증 없는 API의 외부 노출 → 잊힌 API 엔드포인트 |
| USPS Informed Visibility (2018) | 물류 API의 권한 검증 누락 → 통관·물류 시나리오 근거 |

## 5. 프로젝트 반영 방안

| 반영 위치 | 내용 |
|---|---|
| 탐지 파이프라인 — 자산 수집기 | K8s(Service·Ingress·라벨)와 AWS(API Gateway 스테이지, 함수 URL, 보안그룹, 태그) 조회로 미정리 자원 목록화 |
| 분류 규칙 | 소유자 태그 없음 / 장기간 트래픽 없음 / 최근 배포 이력 없음 → Orphan·Dormant 후보 |
| 위험도 점수 | 외부 노출 여부 + 인증 유무 + 소유자 유무 + 마지막 사용 시점 |
| 모의 통관 플랫폼 시나리오 | 계약 종료 포워더 연동 API, 구버전 EDI 조회 API, 테스트 스테이지 등을 의도적으로 남겨 탐지 검증 |
| 제언 | "생성 시 소유자·만료일 태그 의무화", "자격증명 수명주기 관리", "지속적 인벤토리 대조"를 관리 기준에 반영 |
