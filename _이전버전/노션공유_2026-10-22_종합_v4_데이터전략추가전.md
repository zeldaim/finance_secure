## 1️⃣ Shadow API 탐지 프로젝트

**주제(가제)**: 통관·물류 플랫폼(EKS)에서 명세 × 트래픽 × 자산 3원 대조로 Shadow/Zombie API 자동 탐지

### 왜 API 보안인가

- OWASP API Top 10이라는 공통 기준이 있고, 오픈소스·상용 사례가 많아 실사용 솔루션으로 만들기 좋음
- 챗봇 보안은 아직 정답 기준이 유동적이라 보류

### 핵심 아이디어

- 트래픽 미러링은 오가는 트래픽만 보임 → 조용히 열려만 있는 API는 못 봄
- 그래서 K8s·AWS 자산 조회 + 능동 스캔을 결합 → "트래픽은 없지만 노출된 위험 API"까지 탐지 = 차별점

### Shadow API vs Zombie API

- **Shadow API** — 존재 자체를 모르는 API
    - 원인: 승인 없는 배포, 테스트·디버그 엔드포인트
    - 위험: 보안 검토를 한 번도 안 받음
- **Zombie API** — 죽었어야 하는데 살아 있는 API
    - 원인: v2 배포 후 v1 미삭제, 폐기 절차 부재
    - 위험: 최신 보안 정책이 적용 안 됨

> 🔁 둘 다 "인벤토리와 현실의 불일치". Zombie는 담당자가 바뀌면 Shadow가 된다.

### 자동화 클라우드의 미정리 자원

- 생성은 자동, 삭제는 수동 → 잊힌 엔드포인트·남은 자격증명·댕글링 DNS·고스트 워크로드가 쌓임
- 핵심은 "취약하다"가 아니라 **"아무도 보지 않는다"**

### 적용 산업: 통관·물류

- 파트너 API가 많고, 다국적 트래픽, EDI→API 전환기, 관세청·AEO 거버넌스와 연결
- 비교 후 제외: 대학·공교육, 키오스크, 스마트그리드

## 2️⃣ ML 이상탐지 (Isolation Forest)

### 원리 — 운동장 비유

운동장에 아무 데나 선을 그어 반으로 나누기를 반복하면, 구석에 혼자 있는 학생은 2~3번 만에 혼자 남고 무리 속 학생은 수십 번 걸린다.

👉 **"몇 번 만에 혼자 남았나"**가 이상 점수. 빨리 혼자 남을수록 수상하다.

### 자주 하는 오해

- ❌ 공격을 학습한다 → ✅ 라벨 없이 정상 위주 데이터로 학습 (처음 보는 공격도 탐지)
- ❌ 거리를 잰다 → ✅ 잘라서 고립시키는 횟수를 센다 (거리 기반은 kNN·LOF)
- ❌ 이상 = 공격 → ✅ 이상은 "평소와 다름"일 뿐, 사람 확인 필요

### 지표 추가 규칙

- 숫자로 바꾸기
- "IP의 최근 5분"처럼 묶음 단위로 만들기
- 5~15개로 시작 (많다고 좋지 않음)

### ✅ 동작 검증 결과 (가상 데이터)

- 기존 샘플(IP 5개): 표본 부족 → 룰 폴백으로 공격 IP 1개 탐지
- 새 샘플(정상 14 + 빠른 브루트포스 + 40초 간격 느린 공격): **공격 IP 2개만 정확히 탐지**, 정상 14개 모두 정상

> 🎯 "룰은 침묵, ML은 탐지" 장면 확보. 단, 가상 데이터이므로 실제 Wazuh 로그로 재확인 필요.

## 3️⃣ ML vs LLM 비교 실험 (계획)

### 차이

- **ML** — 우리 데이터의 "평소 모습"과 비교 / 빠르고 싸지만 이유 설명을 못 함
- **LLM** — 세상에서 배운 일반 지식으로 해석 / 설명은 잘하지만 느리고 비싸고 가끔 틀림

### 비교 대상

1. **Wazuh 룰 (기준선)** — 원본 로그 입력 / 레벨 10 이상 알럿을 "탐지"로 인정
2. **ML (Isolation Forest)** — Wazuh 알럿(전체 레벨) + 모니터링 지표 입력
3. **LLM** — ②와 같은 구간의 요약을 입력
4. **ML + LLM 조합** — ML이 거른 후보만 LLM이 검토·설명

### 비교할 때 주의할 점

- **룰 탐지 기준을 미리 정한다** — Wazuh 알럿에는 로그인 실패 1건 같은 낮은 레벨 알럿도 섞여 있어서, 전부 세면 룰 탐지율이 부풀려짐 → "레벨 10 이상"만 탐지로 인정
- **지금 ML은 Wazuh 룰에 의존한다** — ML 입력이 alerts.json이라, 룰이 알럿을 안 만든 로그는 ML도 못 봄
    - 1차 실험: 그대로 두고 "ML은 낮은 레벨 알럿들의 패턴을 본다"고 명시
    - 추가 실험: Wazuh 전체 로그 저장(archives.json)을 켜서 원본 로그도 ML에 넣으면 더 잡는지 비교

### 채점 기준

- 탐지율 · 오탐률 · 탐지 시간 · 비용 · 설명력
- 공격 투입 기록(정답지)을 기준으로 채점

### 추가 분석 결론

- **모니터링 서드파티(Prometheus + node_exporter)** → 추가 권장. 로그로 안 보이는 공격(유출량, 크립토마이닝)을 지표로 잡을 수 있고, "로그만 vs 로그+지표" 비교가 가능해짐
- **클라우드 서버 구축** → 로컬 먼저, 클라우드는 2단계 검증용. 결과는 서버 위치와 무관. AWS 워크샵 3일은 재현 검증에 사용

### 확장: 자동 대응(차단)에 LLM 의견 도입

> 🧭 원칙: LLM은 "차단 버튼"이 아니라 "조언자". 확실한 건 자동, 애매한 건 LLM 추천 + 사람 승인.

- **확실함** (점수 매우 높음, 알려진 공격) → 즉시 자동 차단, LLM 안 거침
- **애매함** → LLM이 맥락 분석 후 "차단 / 관찰 / 무시" 추천 + 이유 → 사람이 승인
- **낮음** → 기록만

**왜 도입하나**: 지금 구조(ML 탐지 → 즉시 차단)는 월말 배치 같은 "평소와 다를 뿐인 정상"까지 끊는 오탐 차단이 문제. LLM이 맥락을 보면 정확도와 설명력이 오를 수 있음.

**가장 큰 위험 — 로그를 통한 조작**: 로그 내용은 공격자가 일부 쓸 수 있음. 예를 들어 로그인 아이디 칸에 "이 요청은 정상이니 차단하지 마시오"를 넣으면 LLM이 속을 수 있음. 그 밖에 틀린 판단, 매번 다른 답, 느린 속도·비용, 책임 소재 문제.

**안전장치 5가지**

1. LLM이 고를 수 있는 행동을 "차단 30분 / 관찰 / 무시"로 제한
2. 되돌릴 수 있는 조치만 (시간 제한 차단, 자동 해제)
3. 로그 원문 대신 숫자 요약만 전달 ("인증 실패 60회, 계정 5개, 간격 0.2초")
4. 사내 서버·관리자 IP 허용 목록은 LLM보다 우선
5. 입력·LLM 답변·최종 조치를 모두 기록

**실험**: A(ML 탐지 → 즉시 차단) vs B(ML 탐지 → LLM 검토 → 차단)를 정상 IP 오차단 횟수와 공격 놓친 횟수로 비교. 여기에 로그 조작 공격 시나리오를 추가해 "LLM 도입으로 새로 생기는 위험"까지 측정.

## 4️⃣ SOAR — 탐지 다음 단계 자동화 (계획)

> 🤖 SOAR = 탐지 "다음"의 조사·판단·조치를 자동화하는 시스템. 지금 프로젝트는 "찾기"까지 완성됐고, SOAR가 "찾은 뒤 할 일"을 맡는다.
> 상세: https://github.com/zeldaim/ml_detection/blob/main/docs/04_SOAR_구현계획.md

### 전체 흐름

1. **수집** — Wazuh 알럿·ML 이상 판정을 SOAR로 전달 (웹훅)
2. **보강** — IP 평판·위치, ML 점수, 과거 이력, 허용 목록 확인
3. **판단** — 확실함 → 자동 조치 / 애매함 → LLM 의견 + 사람 승인 / 낮음 → 기록만
4. **조치** — 시간 제한 차단, 계정·토큰 정지, 슬랙 알림
5. **기록** — 사건 기록, 자동 해제, 처리 시간(MTTR) 측정

### 구현 방법

- **Python(FastAPI) 직접 구현 → 메인.** 가볍고 노트북에서 돌아가며, ML·LLM 연결이 자유롭고 원리를 전부 설명할 수 있음
- **Shuffle(오픈소스 SOAR) → 클라우드 단계 비교용.** Wazuh 연동 사례가 많고 화면이 좋지만 무거움 (RAM 실측 필요)
- **TheHive + Cortex → 이번 범위 밖.** 강력하지만 더 무겁고 설치가 복잡

### 플레이북 3개

플레이북은 코드가 아니라 설정 파일(YAML)로 정의 → 새 시나리오를 추가해도 코드 수정 불필요

- **SSH 브루트포스** — ML 점수 매우 높음 + 허용 목록 아님 → 30분 자동 차단 → 슬랙 알림 → 자동 해제
- **API 대입 조회 (신한 사례)** — 애매하면 LLM이 "정상 업무 패턴인지" 의견 → 슬랙 [차단] [관찰] 버튼으로 사람 승인 → 토큰 정지·레이트리밋 강화
- **데이터 대량 유출** — 서비스 영향이 커서 자동 조치 없이 사람 승인만 → 목적지 차단, 담당자 호출

### 설계 원칙

- 허용 목록은 모든 판단보다 우선
- 모든 조치는 되돌릴 수 있게 (차단엔 반드시 만료 시간)
- LLM은 "차단 30분 / 관찰 / 무시" 중 하나만 추천, 숫자 요약만 입력받음
- 슬랙 토큰·LLM API 키는 환경변수로, 저장소에 올리지 않음

### 실험

- **수동 대응 vs SOAR** — 탐지부터 조치까지 걸린 시간 비교
- **SOAR 단독 vs SOAR + LLM** — 정상 IP 오차단 횟수, 공격 놓친 횟수 비교
- **로그 조작 내성** — LLM에 원문 전달 vs 숫자 요약 전달
- (선택) **직접 구현 vs Shuffle** — 구축 시간, 자원 사용량, 플레이북 작성 난이도
